Cel i zakres etapu

Celem etapu 1 jest działający szkielet aplikacji Metadata Analyzer: dwa niezależne interfejsy (WPF i CLI), wspólna logika, wspólne modele danych, rejestrowanie przebiegu działania w pliku tekstowym oraz testy jednostkowe najważniejszych funkcji.

Etap 1 nie zawiera prawdziwej analizy metadanych przez System.Reflection ani bazy danych — dane pochodzą z dostawcy symulowanego, a logger zapisuje wyłącznie do pliku. Oba elementy są przygotowane do wymiany w kolejnych etapach dzięki interfejsom i wstrzykiwaniu zależności.

Zakres dostarczony:

  • rozwiązanie z 5 projektami (Core, Infrastructure, WPF, CLI, Tests),
  • pełna hierarchia modeli metadanych,
  • dostawca danych symulowanych SampleLibrary.dll,
  • serwis logiki MetadataService + formatter prezentacji tekstowej,
  • logger plikowy z poziomami INFO/WARNING/ERROR,
  • okno WPF w MVVM (drzewo, panel szczegółów, pasek statusu),
  • aplikacja konsolowa z menu i obsługą błędnych danych wejściowych,
  • 54 testy jednostkowe (xUnit + Moq),
  • konfiguracja appsettings.json i kompozycja DI.

3.5. Odwzorowanie zagnieżdżeń

AssemblyModel (1) ──> NamespaceModel (*) ──> ClassModel (*)
                                                ├── MethodModel (*) ──> ParameterModel (*)
                                                ├── PropertyModel (*)

Typy zwracane i typy parametrów są przechowywane jako nazwy ("User", "int", "IUserRepository"), co pozwala odwoływać się do typów spoza analizowanego zestawu bez cyklicznych referencji obiektowych. W etapie 2, przy analizie przez System.Reflection, te nazwy będą uzupełniane o informację, czy typ należy do analizowanego zestawu.

3.6. List<T> czy ObservableCollection<T>

Modele w Core używają IReadOnlyList<T>, ponieważ dane przekazywane są jako gotowy, niezmienny model. Kolekcja obserwowana (ObservableCollection<TreeNodeViewModel>) występuje wyłącznie w warstwie WPF — tam, gdzie drzewo jest bezpośrednio obserwowane przez kontrolkę TreeView.

5. Usługi Core

5.1. MockMetadataProvider

Buduje pełne drzewo SampleLibrary.dll w metodzie LoadAsync. Dane tworzone są w providerze, a nie w ViewModelu — zgodnie z wymaganiem etapu. Metoda BuildAssembly(DateTimeOffset) jest publiczna i statyczna, dzięki czemu można jej użyć w testach bez zależności od zegara.

Czas LoadedAt pochodzi z ISystemClock (wstrzyknięty przez konstruktor, opcjonalny):

public sealed class MockMetadataProvider(ISystemClock? clock = null) : IMetadataProvider

5.2. MetadataService

Odpowiedzialności:

  • uruchomienie analizy (AnalyzeAsync) i odświeżenia (RefreshAsync),
  • wywołanie providera i zapamiętanie wyniku w Current,
  • logowanie startu, sukcesu, anulowania i błędu,
  • serializacja równoległych wywołań (SemaphoreSlim, IDisposable),
  • propagowanie wyjątku do interfejsu po zalogowaniu.

Przepływ LoadAsync:

LogInformationAsync(startMessage)
  └─ provider.LoadAsync(token)
       └─ Current = assembly
            └─ LogInformationAsync("Sample data loaded: …")
  wyjątek? → LogErrorAsync("Metadata analysis failed: …") → rethrow
  anulowanie? → LogWarningAsync("Metadata loading cancelled") → rethrow
  finally → _gate.Release()

5.3. MetadataProviderResolver

Cienka warstwa decyzyjna pozwalająca zachować kontrakt UseMockData z konfiguracji bez komplikowania kompozycji DI. Gdy UseMockData = false (etap 2, jeszcze niezaimplementowany), rzuca NotSupportedException z czytelnym komunikatem zamiast po cichu zwracać dane mockowe.

5.4. MetadataFormatter

Trzy operacje formatowania tekstu:

MetodaWynikUżycie
FormatTreedrzewo ASCII z wcięciamiCLI (opcja 2), logi, eksport
FormatDetailspodsumowanie zestawu + lista przestrzeni i klasCLI (opcja 3)
FormatMemberDetailsszczegóły jednego składnika klasyCLI (opcja 4)

Przykład FormatTree:

Assembly: SampleLibrary
Version: 1.0.0.0

|   +-- Namespace: SampleLibrary.Models
    |   +-- Class: User
        |   +-- Property: Id (int)
        |   +-- Property: Name (string)
        |   +-- Constructor: public ()
        +-- Method: GetFullName() : string
    +-- Class: Product
        |   +-- Property: Id (int)
        |   +-- Property: Price (decimal)
        |   +-- Constructor: public ()
        +-- Method: CalculateTax() : decimal
|   +-- Namespace: SampleLibrary.Services

Szczegóły implementacyjne:

  • wcięcie to powtórzone " " na każdy poziom (GetIndent), connector +-- lub | +-- ,
  • kolejność składników jest deterministyczna: pola → właściwości → konstruktory → metody,
  • całe formatowanie używa CultureInfo.InvariantCulture (reguła CA1305 jako błąd kompilacji),
  • puste modele (AssemblyModel.Empty()) obsłużone jawnie ("Assembly contains no namespaces."),
  • nieznany składnik → "Member: Missing (not found)" zamiast wyjątku.

7.3. Zachowanie przy awarii zapisu

Logger nigdy nie przerywa działania aplikacji. Gdy zapis do pliku jest niemożliwy, próbuje poinformować o tym konsolę ([logging failure] …), a wywołanie kończy się sukcesem. Test LogWriteFailureDoesNotThrow weryfikuje ten scenariusz, wskazując jako cel plik katalogu (konstrukcja path/application.log, gdzie path jest plikiem).

7.4. Logowanie do konsoli

LoggingOptions.LogToConsole domyślnie true, ale oba interfejsy wyłączają je (logToConsole: false), aby log nie zaśmiecał prezentacji CLI i nie był bezużyteczny w WPF. Można je włączyć jednym parametrem — przydatne przy diagnostyce.

9.3. Polecenia

CommunityToolkit.Mvvm generuje implementacje ICommand z atrybutów:

[RelayCommand]
private async Task AnalyzeAsync(CancellationToken cancellationToken) { … }

[RelayCommand]
private async Task RefreshAsync(CancellationToken cancellationToken) { … }

[RelayCommand]
private void ClearSelection() { … }

Generatory tworzą AnalyzeCommand, RefreshCommand, ClearSelectionCommand (typ AsyncRelayCommand dla metod asynchronicznych — z blokadą ponownego wykonania w trakcie pracy i przekazywaniem CancellationToken). Dzięki temu w projekcie nie ma ręcznie pisanych RelayCommand/AsyncRelayCommand ani powtarzalnego INotifyPropertyChanged.

9.4. Powiadamianie o zmianach

[Fact]
public async Task SelectingNodeUpdatesDetailsWithoutReloading()
{

}

13.2. Zgodność z clean code

  • Jedna odpowiedzialność: model / provider / serwis / formatter / logger / ViewModel / widok.
  • Brak komentarzy — nazwy metod mówią, co robią (TryParseIndex, DescribeConstructor, AppendChildren, ResolveLogFilePath).
  • Brak duplikacji: LogEvents (komunikaty), DetailsViewModel (fabryki szczegółów), ConsolePresentation (warstwa wizualna CLI), GetIndent (wcięcia drzewa).
  • Małe metody, wcześnie wychodzące (return, continue), maksymalnie jedna decyzja na metodę.
  • Zabezpieczenia kontraktów: ArgumentNullException.ThrowIfNull, ArgumentException.ThrowIfNullOrWhiteSpace, NotNullWhen(true) w TryGetAssembly.
  • Niezmienność modeli i DetailsViewModel; brak setterów publicznych tam, gdzie nie są potrzebne.
  • Asynchroniczność z CancellationToken od UI po provider; brak .Result/.Wait() w kodzie produkcyjnym.
  • Obsługa błędów na granicy warstw (serwis loguje i propaguje, UI prezentuje, logger nigdy nie rzuca).
  • Formatowanie niezależne od kultury — wymuszone przez analizator CA1305 (błąd kompilacji).
  • Testy czytelne jak specyfikacja — nazwy w stylu AnalyzeFailureShowsErrorAndLogsIt.
  • Kod ostrzeżeń zero — brak #pragma warning disable, brak <NoWarn>.

13.3. Znane ograniczenia etapu 1

  1. Dane pochodzą wyłącznie z mocka — brak analizy rzeczywistych plików .dll.
  2. Logowanie tylko do pliku; logger bazodanowy zarezerwowany na etap 4 (Logging:Provider).
  3. Brak wyszukiwania i filtrowania w drzewie (etap 2+).
  4. Brak eksportu raportu (JSON/CSV) — IMetadataFormatter jest na to przygotowany.
  5. Ustawienia są tylko do odczytu z appsettings.json (bez edycji w UI).
  6. Brak testów UI (widoków XAML) — testowane są ViewModele i logika; zgodnie z wymaganiem etapu.
  7. Application:UseMockData = false rzuca NotSupportedException do czasu implementacji refleksji.
  8. Aplikacja WPF działa tylko na Windows (WPF nie jest cross-platform).
